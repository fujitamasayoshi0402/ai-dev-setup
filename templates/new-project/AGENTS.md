## 進め方のルール
- 利用者はプログラミングがわからない。専門用語には短い説明を添える
- 作業を始める前に、何をするかを3行以内で説明してから進める
- 作業が終わったら、何を変えたかと、どうやって確認すればよいかを伝える
- 新しい道具（ライブラリなど）を追加する前に、理由を説明して確認を取る
- 利用者が書いた文章や情報（例: 住所・電話番号）は、勝手に書き換えない
- 回答とコミットメッセージは日本語
- `.env` の中身（パスワードなど）は読まない・表示しない

- AI が自分で動かして確認し、確認した内容を報告すること

## 会話の整理（AI から利用者への案内）
会話は長くなるほど、古い話に引っぱられて精度が落ちる。次のタイミングで、利用者にコマンドを**案内する**（コマンドは利用者が打つ。AI は自分では実行できない）。

| タイミング | 案内すること |
|---|---|
| 話題や仕事が大きく変わったとき | 「新しい会話にしましょう」→ 下の「新しい会話にする」コマンド |
| 1つの会話が長くなったとき（何十往復もした・前の話を忘れ始めた・返事が遅くなった） | 「会話を要約して軽くしましょう」→ 下の「会話を要約する」コマンド |

- 案内する前に、続きに必要なこと（決まったこと・次にやること）を`docs/` のメモ（または引き継ぎメモ `HANDOFF.md`）に書き残し、「書き残したので、新しい会話でも続きができます」と伝える
- 新しい会話では、利用者に「〇〇の続きをしたい」と言ってもらえばよいことも伝える

## スキル
- スキルは `.agents/skills/<名前>/` と `.claude/skills/<名前>/` の両方に同じ内容で置く
- 外部から取り込んだスキルは `.agents/skills/SOURCES.md` に記録する
- 取り込むときは中身を確認し、利用者の了承を得てから入れる

## Git（変更の保存）
- ひと区切りごとに、小さくコミット（保存）する
- 新しい作業は、ブランチ（Orca では worktree）を分けて行う
- GitHub を使っていない場合: 作業が終わったら、利用者の確認を取ってから `main` に取り込む
- GitHub を使っている場合: `main` に直接コミットせず、PR を出す
